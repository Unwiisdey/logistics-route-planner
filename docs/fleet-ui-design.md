# 双车 UI 设计方案（本次不改 UI 代码）

目标：保留现有地图和模拟操作，让使用者能同时看清两辆车的位置、订单归属和各自任务。当前正式网页仍运行单车 Simulation；以下接口和画面均为后续设计，尚未实现。

## 页面安排

```text
┌ 共享时钟 08:05   开始/暂停   步长   重置   订单/处罚总计 ┐
│                                                   │
│                  同一张道路网络                    │
│         蓝色 V01 →          橙色 V02 →              │
│         红色拥堵路段；已走/在途/待走使用线型区分      │
│                                                   │
├ V01：行驶中 · 载重 · 当前任务 · 下一站 ETA · 返仓 ETA ┤
│ 后续路径 / 当前任务 / 任务路径（取货→配送→返仓）      │
├ V02：卸货中 · 载重 · 当前任务 · 下一站 ETA · 返仓 ETA ┤
│ 后续路径 / 当前任务 / 任务路径（取货→配送→返仓）      │
├ 手动订单：取货仓库、目的地、数量、窗口、紧急程度      ┤
│ 提交后：分配 V02；预计送达；或两车拒绝原因            │
├ 订单表：订单 ID / 所属车辆 / 状态 / 实际迟到 / 处罚   ┤
│ 日志筛选：全部 / V01 / V02 / 订单分配 / 共享路况       │
└───────────────────────────────────────────────────┘
```

桌面端地图与车辆卡片可分左右两栏；窄屏改为上方地图、下方两张卡片。单击车辆或卡片可聚焦其路线，但地图始终显示两辆车。路线重叠时，选中车辆加粗，另一辆使用细虚线；拥堵使用红色道路底线，避免覆盖车辆归属色。不能仅依赖颜色区分，应同时显示 V01/V02 标签。

## 操作与反馈

- 一个播放/暂停控制共享时钟，两车同时推进；不设置会令时钟分叉的“单独运行某车”按钮。
- 手动提交默认自动分配，呈现系统选择的车辆和预计送达时刻；暂不提供强制换车或拖拽订单，保持归属固定。
- 当前任务、任务路径、后续道路路径分别按车辆展示，避免把道路途经节点误认为配送任务。返仓车辆显示“空闲，等待新订单”。
- 订单归属写入订单表；已完成订单保留原归属。拒绝时列出两车的原因，不能只显示笼统失败。
- 每车分别显示载重/上限、完成数量、超时数量、处罚；顶部显示总计。处罚仍为迟到分钟向上取整 × 1，费用另列。
- 道路标签显示“当前路况预计耗时”；车辆在途卡片显示“入边锁定总耗时/剩余时间”，延续现有耗时解释。新路径短时高亮，并注明重规划车辆、原因和更新 ETA。

## 后续桥接接口建议

保留现有单车接口作为兼容入口，新增明确的 fleet 模式。服务端持有一个 FleetSimulation；一次 advance 只推进共享时钟一次。

建议返回共享 time/nodes/edges，加 vehicles 数组（id、位置、状态、载荷、道路路径、当前任务、取送任务序列、ETA、完成/迟到/处罚），以及带 vehicle_id 的 orders/events/assignments。insert_order 返回 FleetAssignment，不由浏览器自行决策分单。

路线、时间窗口和处罚均由 C++ 计算，网页负责输入与显示。不得让前端为两辆车创建独立路况随机源或各自时钟。

## 后续验收

同图显示两辆车；两车时间一致；新订单只进入一车；既有归属不变；两车均不可接时原因完整；一次路况对两车可见；提前返仓车辆显示空闲；在途锁定耗时与道路标签区分；缩放、窄屏与重叠路线可读。本次仅交付本方案，不宣称这些画面已经实现。
