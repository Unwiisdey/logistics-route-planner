# 电商物流配送路径规划系统需求拆解

## 依据与阶段范围

依据课程题目《第2题 电商物流配送路径规划系统》完整原文及本次 C++17 项目初始化要求。本文将“原文基本要求”“原文扩展要求”“原文实现提示”和“设计建议/待定项”分开，防止将示例参数或讨论方案误写成教师要求。

当前最终版本为 v1.0.0，已完成第 1—7 阶段本次范围。第 7 阶段补充有界最短路缓存、图版本失效、综合与性能测试、设计/用户/API/测试文档、一键演示及答辩材料。已接入正式本地 Web 界面，保留接单时全部窗口、取货、容量检查；2026-10-24 经用户确认改为迟到分钟向上取整 × 每分钟分值，默认 1 分/分钟。用户追加要求已实现基础双车调度、省时兜底、新版 82 边路网与中转站取货，正式 UI 已采用批准的双车 Demo 布局；真实交通接入不在当前范围；题目中的其他扩展点不因发布最终版而自动视为已完成。

## 功能需求

### FR-01 图数据结构

**原文基本要求：** 使用有向带权图表示网络。节点有唯一 ID，类型包括仓库、配送点和中转站；道路包含距离（公里）、预计耗时（分钟）和运输成本（元）。节点总数 ≥30，至少 2 个仓库、15 个配送点、3 个中转站，道路总数 ≥50。支持动态添加/删除节点和边，输出邻接表或邻接矩阵。

**设计与现状：** 采用原文提示的邻接表。`Graph` 私有保存节点索引和按起点分组的出边；边额外有 ID，方便车辆在途定位和高亮。双向通行使用两条有向边表示。现已实现封装、校验和只读查询；删除节点会清理关联道路。节点与边分别使用 `Node.h/.cpp`、`Edge.h/.cpp`。

**验收点：** 演示数据满足全部数量条件；方向正确；ID 不重复；删除节点时清理入边和出边；不存在悬空引用。活动路线引用被删除节点/道路时，必须使相关计划失效或触发重新评估。

**简化子网络：** 按第 5 阶段允许的简化，中转站作为连接节点，子网络展开到同一有向图、使用全局唯一 ID 即可参与路径搜索。经 2026-10-25 用户批准，现可作为动态订单的指定取货点；仍不实现递归图对象、中转补货、车辆间货物交接或分级车队调度。

### FR-02 配置加载

**原文基本要求：** 通过配置文件定义节点坐标和类型、道路初始权重、车辆载重上限、订单列表（配送点 ID、货物量、时间窗口）。

**设计与现状：** 第 2 阶段使用固定版本 nlohmann/json 单头文件，`ConfigLoader` 从文件/流加载网络并返回 `Graph`，不会暴露 JSON 类型给业务层。校验 ID、端点引用、类型、有限非负权重及窗口顺序，给出位置明确的错误。格式见 [配置说明](../config/README.md)。`Configuration` 保留为未来包含车辆、订单的全量配置原型，当前尚不解析这些字段。

**第 5 阶段补充：** `OrderConfigLoader` 解析独立订单文件的初始订单和动态发布时间；支持数量、窗口、取货仓库和优先级，拒绝重复键/ID、未知字段及非法数值。车辆参数仍由 CLI 配置，尚未统一到 `Configuration`。

**验收点：** 可以从文件构造网络、车辆和订单；坏数据明确报错；提供满足题目规模的独立演示数据。小型测试数据可低于演示规模。

### FR-03 基础路径规划

**原文基本要求：** 基于订单需求与车辆信息生成配送路径；单车辆从仓库出发，遍历所有待配送点后返回仓库。支持最短距离（基于 Dijkstra）和最低成本（使用边成本权重）两种策略。

**第 3 阶段实现：** 两点路径使用 Dijkstra，距离/成本均使用对应边权并跳过关闭道路；配送顺序按最新要求使用贪心最近邻，沿最短路途经其他待配送点时同时服务。路线记录完整节点和道路序列、配送停靠点、三项累计量及预计到达时间。服务时间暂为 0，窗口尚不执行。每个配送点只安排一次服务，但道路和通行节点可以重复经过。

**最优性口径已明确：** 本阶段按用户要求使用贪心最近邻 + Dijkstra，不承诺整条巡回路线全局最优。成本贪心甚至可能得到比距离贪心更贵的完整路线；示例中如实保留该现象。后续插入法、局部优化或小规模精确算法可以作为单独迭代。

**载重与仓库现状：** 默认从字典序最小的仓库出发，支持显式选择并返回该仓库。提供可选 capacity_kg，检查全部所选节点默认需求量之和；省略时不校验载重。超载反馈失败，不默认回仓补货、多车或多趟。后续独立订单需要以实际货物量替代节点默认需求量。

**第 4 阶段补充：** 仿真模式始终校验载重，未指定时默认 1000 kg，一次装载全部选定任务。`Planner::schedule()` 在已有路线基础上加入等待和卸货的预计时间，`Simulation` 执行实际时间推进；不会每个时钟步长重复计算路径，也未新增满足窗口的访问顺序搜索。

**第 5 阶段补充：** 订单模式使用独立订单数量与窗口，初始按优先级/截止时间处理并尝试插入；动态订单枚举取送插入位置，保留旧动作相对顺序。逐段 Dijkstra 后检查全部窗口、取送先后、每次装卸货后的容量及返仓。支持同点多单，仅执行指定订单停靠，途经节点不自动配送。采用启发式搜索，不保证全局最优或找到所有可能的可行解。

**验收点：** 两种策略可切换；路线方向与道路一致；覆盖所有被接受的待配送订单且返回出发仓库；检查载重；不可达或未找到可行计划时反馈原因，不输出伪成功结果。

### FR-04 时间窗口

**原文扩展要求：** “加入时间窗口硬约束”，超出规定时间送达则标记“超时订单”并记录 penalty。

**本次确认：** 第 5 阶段在计划/接单阶段严格检查全部剩余窗口；无法满足则不接受初始计划或动态请求。运行阶段仍记录实际超时与按分钟计算的处罚。保留第 4 阶段兼容模式用于既定路线迟到演示，不将其称为硬约束模式。

**已实现规则：** 对窗口 `[earliest, latest]`，开始卸货时间 `service_start = max(arrival, earliest)`；迟到分钟数 `max(0, service_start - latest)`。按开始卸货而非卸货完成判断窗口，恰好截止开始视为按时。卸货默认 2 分钟、可配置为 0 或其他非负值；完成后扣减载荷并记录 delivered_at。无窗口时无需等待且不会因时间超时。

**当前处理：** `--scenario` / `--hard-windows` 启用严格模式。动态请求失败只追加拒绝记录，保留原车辆、任务与路线；已承诺的当前服务若迟到也拒绝增加新任务。数字边界使用 1e-9 分钟容差消除浮点舍入，非业务宽限。启发式失败只能表述为“未找到可行插入”，不能证明不存在可行解。

**penalty 最新确认（2026-10-24）：** 原文没有公式；用户将此前每单固定处罚改为 `ceil(late_minutes) × late_penalty_per_minute`，默认 1 分/分钟。迟到以开始卸货时计算，未迟到为 0；不足一分钟向上取整，2 分 30 秒计 3 分。使用 `--late-penalty-per-minute` 配置费率，旧 `--late-penalty` 为同义别名。完成配送时每单只记一次，处罚分和运输成本分开统计。窗口判定和整分钟边界仅忽略 1e-9 分钟的浮点噪声，不是业务宽限期。

**验收点：** 早到、按时、恰好截止和迟到均正确处理；区分预计迟到和实际超时；处罚记录可追溯。

### FR-05 动态订单

**原文要求：** 配送过程中响应新订单；扩展要求插入紧急订单并优先满足，如“1 小时内送达”。

**已实现：** `DynamicOrder::insert()` 枚举取货/送货插入位置；`Simulation::insert_order()` 仅接受完整剩余路线可行的候选。紧急新订单优先按最早开始卸货选择，再比较距离/成本；普通订单按目标代价选择。相同发布时间按文件顺序处理，不承诺多个紧急单之间的全局最优排序。拒绝请求不加入已接受任务，不取消旧订单。

**取货与容量规则已确定：** 动态货物位于订单的指定仓库，必须实际到仓库后才能装货；装货默认零耗时。初始订单一次装载，动态订单可先配送旧货再取货以腾出空间。规划及执行都校验容量；接单时不增加载荷，卸货完成才扣减。允许其他仓库取货，最终仍回本车出发仓库。

**验收点：** 配送途中可新增订单；成功时只更新剩余任务；失败时保留原有可行计划并说明原因；已完成订单不重复配送。

### FR-06 模拟时钟

**来源：** 本次用户明确提出，也是时间窗口、在途状态与路况事件的实现支撑；题目没有单列时钟操作要求。

**已实现：** `SimClock` 使用相对模拟日开始的连续分钟数，默认 480（08:00），步长默认 5，可配置。支持 `advance()`、`advance(minutes)`、`now()`、`format()`；跨天显示 `D+1 HH:MM`。不调用推进即暂停。`Simulation` 在一个步长内按事件时刻处理全部到达、等待结束与卸货完成，不把事件延迟到下一采样点。

**验收点：** 时间单调推进，暂停不推进；等待、行驶和截止判断共用时钟。模拟时间与墙上实际经过的时间不混用。

### FR-07 车辆当前位置

**来源：** 本次用户明确提出，也是动态重规划的必要运行状态；题目未规定具体表示方法。

**已实现：** `Vehicle` 封装 ID、载重上限、当前载荷、仓库及状态（空闲、行驶、等待、卸货），状态只读查询，交由仿真执行转换。`VehiclePosition` 的节点 ID 与道路 ID 互斥；行驶段记录 from/to、总耗时及剩余时间，提供连续进度。车辆坐标按两端点线性插值。只在任务完成后扣载荷，重复通行不重复配送。

**在途衔接已实现：** 行驶中的当前边不可中断，等待/卸货中的当前服务不可中断。在其完成节点、完成时刻及预计剩余载荷上评估新路线，届时切换；不会把车辆瞬移回仓。连续插单保留先前已接受订单。每版路线保存编号，历史快照引用对应版本。实时封路或删边规则仍留待后续。

**验收点：** 位置随时钟推进；路线更新不使车辆跳回仓库；已完成配送和已走过道路不会被重复执行。

### FR-08 实时路况与重规划

**原文扩展要求：** 道路具有拥堵、畅通等动态属性；因拥堵导致某条路径耗时增加 20%以上时自动触发重新规划，并在界面更新路径高亮。

**第 6 阶段实现：** `TrafficSimulator` 默认每 0.5 模拟分钟选择 `ceil(可模拟道路数 × 10%)` 条边，畅通转拥堵时耗时为初始值的 1.2～2.0 倍，拥堵转畅通时恢复初始值。零初始耗时和关闭道路不参加随机模拟。间隔、比例、种子可通过 CLI 配置，倍率通过 C++ 配置；保留初始与当前耗时并记录每批变化。

**本次明确：** 阈值含 20%，相对事件前耗时计算，比较容差 1e-12；不变/恢复不重复触发；外部事件从零增为正触发。每个事件时刻先更新路况，再处理同刻到达及出发；CLI 同刻动态订单在推进返回后处理。当前行驶段保持入边耗时，等待/卸货不中断。

**增量范围：** `Replanner` 按剩余取送停靠及返仓划分区间，只对包含触发道路的区间执行耗时最短搜索，其余路径不变；保留动作顺序及容量约束。点到点 Dijkstra 在目标确定后停止，未运行全点对最短路，也不重算完整任务顺序；单个区间最坏仍可遍历整个连通分量。对所有剩余动作线性刷新 ETA 和窗口风险。初始 distance/cost 策略保持不变，拥堵修复改按耗时以减少延误，因此距离/成本可能增加。

**约束反馈：** 无更快绕路时可保留原路径；预测迟到的已接订单继续执行并记录风险，实际完成时按迟到分钟向上取整计罚。新订单仍须满足全部剩余窗口。低于触发阈值或恢复畅通时只刷新 ETA，不主动重搜捷径。`apply_traffic()` 保留外部确定性事件接口，当前只接受畅通/拥堵，不支持运行中封路、删边或真实在线交通接口。

**原文实现提示与本次选择：** 30 秒、10% 来自原文示例及本次用户要求，作为可配置默认值；选取比例无法为整数时向上取整。随机种子在相同标准库/工具链中可复现；导出的路况历史可跨环境回放。

**验收点：** 检查阈值两侧及边界、连续事件；触发后基于车辆状态与未完成订单重新评估；界面展示当前路况和有效路线。

### FR-09 可视化

**原文基本要求：** 图形界面展示节点位置、道路方向、权重标签；扩展要求在重规划后更新路径高亮。

**第 3 阶段实现：** 按本次允许的简化方案，C++ 的 `Visualizer` 导出 5 份 CSV，Python/matplotlib 读取并生成网络与路线图，展示节点坐标、类型、有向箭头、选定权重与路线步号。支持可选绘图窗口，暂不提供集成式动态调度 GUI。既有 `NetworkView` 接口保留供后续使用；窗口/路况变化后的自动刷新仍属后续范围。

**第 4 阶段实现：** 新增车辆快照、事件、配送记录和仿真参数 CSV；Python 按快照展示车辆星形标记及已走/当前/未走路径颜色。支持单帧 PNG、GIF、时间滑块与播放/暂停。此模式回放已导出状态，未实现实时进程通信；后续路况重规划后的在线刷新仍需接入。

**第 5 阶段输出：** 动态路线使用独立版本、取送动作、插入决定 CSV 及日志展示。旧绘图器明确拒绝动态版本，防止用新路线解释旧状态；本次未要求新增动态图形回放。

**第 6 阶段实现：** `plot_traffic.py` 读取初始网络、路况历史、生效路线版本、每帧待执行路径与跨版本行驶记录。展示拥堵、当前边、更新路线、车辆坐标和下一配送/返仓 ETA，支持单帧 PNG、时间滑块、播放/暂停；倒退回放不会残留新路况。路况历史按版本而非仅按时间截断，可区分同刻事件。图形回放导出数据，不宣称已连接运行中的 C++ 进程。

**验收点：** 节点坐标与配置对应；方向及权重可辨识；高亮对应当前路线，重规划后旧高亮不会残留。时钟、车辆位置与订单状态展示属于配合动态功能的设计建议。

## 实现前需明确的规则

规则的落实状态如下：

1. 第 2 阶段已明确：JSON 网络格式、示例需求量单位 kg、时间单位分钟。初始仓库和模拟开始时间字段将在加载车辆/订单时补充。
2. 第 3 阶段已明确：贪心最近邻 + Dijkstra；CSV + Python/matplotlib 绘图；可选的单次装载量校验。没有提前实现动态订单或窗口约束。
3. 第 4/5 阶段已明确：窗口在开始卸货时判定、默认卸货 2 分钟、原阶段每单固定处罚；当前已按用户确认改为迟到分钟向上取整、默认 1 分/分钟；硬模式接单前检查全部约束，仓库实际取货，当前路段/服务完成后衔接。
4. 第 6 阶段已明确：相对事件前耗时、含 20%、零转正触发、按取送区间修复、当前边入边耗时锁定；运行中封路/删边不在本次范围。

第 7 阶段原范围未新增数据库、联网地图、账户系统、多车辆调度、真实 GPS 或真实交通接入；随后用户明确新增的双车扩展见下节。

## 用户追加：省时兜底与基础双车（2026-10-24）

- 订单模式若距离/成本候选因时间窗口不可行，改用耗时最短重试同一动作序列；可行后再参与原距离/成本候选比较。拒绝仍须表述为未找到可行方案，不保证全局可行性或最优。

按用户批准采用简化主路/支路/捷径布局，保留 30 个节点、配置 82 条有向边，含 D12 ↔ D18。每条道路具有明确距离、耗时、成本；仍满足课程规模。
