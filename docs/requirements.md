# 电商物流配送路径规划系统需求拆解

## 依据与阶段范围

依据课程题目《第2题 电商物流配送路径规划系统》完整原文及本次 C++17 项目初始化要求。本文将“原文基本要求”“原文扩展要求”“原文实现提示”和“设计建议/待定项”分开，防止将示例参数或讨论方案误写成教师要求。

当前已完成第 1—3 阶段：图与 JSON 网络加载、Dijkstra、最近邻单车辆往返配送、三项总量、CSV 导出及 Python 简单可视化。按照第 3 阶段最新要求，采用贪心访问顺序而非严格全局最优，允许 Python 绘图。当前仍只加载节点/道路，车辆与订单配置、时间推进、窗口执行及动态重规划尚未实现。以下全量验收点不能视为均已完成。

## 功能需求

### FR-01 图数据结构

**原文基本要求：** 使用有向带权图表示网络。节点有唯一 ID，类型包括仓库、配送点和中转站；道路包含距离（公里）、预计耗时（分钟）和运输成本（元）。节点总数 ≥30，至少 2 个仓库、15 个配送点、3 个中转站，道路总数 ≥50。支持动态添加/删除节点和边，输出邻接表或邻接矩阵。

**设计与现状：** 采用原文提示的邻接表。`Graph` 私有保存节点索引和按起点分组的出边；边额外有 ID，方便车辆在途定位和高亮。双向通行使用两条有向边表示。现已实现封装、校验和只读查询；删除节点会清理关联道路。节点与边分别使用 `Node.h/.cpp`、`Edge.h/.cpp`。

**验收点：** 演示数据满足全部数量条件；方向正确；ID 不重复；删除节点时清理入边和出边；不存在悬空引用。活动路线引用被删除节点/道路时，必须使相关计划失效或触发重新评估。

**范围说明：** 原文描述中转站“可嵌套子配送网络”，但未在基本功能中明确强制实现层级调度。本项目先将中转站作为普通类型节点参与通行，嵌套网络列为待确认扩展，不自动增加多车辆或分级配送要求。

### FR-02 配置加载

**原文基本要求：** 通过配置文件定义节点坐标和类型、道路初始权重、车辆载重上限、订单列表（配送点 ID、货物量、时间窗口）。

**设计与现状：** 第 2 阶段使用固定版本 nlohmann/json 单头文件，`ConfigLoader` 从文件/流加载网络并返回 `Graph`，不会暴露 JSON 类型给业务层。校验 ID、端点引用、类型、有限非负权重及窗口顺序，给出位置明确的错误。格式见 [配置说明](../config/README.md)。`Configuration` 保留为未来包含车辆、订单的全量配置原型，当前尚不解析这些字段。

**验收点：** 可以从文件构造网络、车辆和订单；坏数据明确报错；提供满足题目规模的独立演示数据。小型测试数据可低于演示规模。

### FR-03 基础路径规划

**原文基本要求：** 基于订单需求与车辆信息生成配送路径；单车辆从仓库出发，遍历所有待配送点后返回仓库。支持最短距离（基于 Dijkstra）和最低成本（使用边成本权重）两种策略。

**第 3 阶段实现：** 两点路径使用 Dijkstra，距离/成本均使用对应边权并跳过关闭道路；配送顺序按最新要求使用贪心最近邻，沿最短路途经其他待配送点时同时服务。路线记录完整节点和道路序列、配送停靠点、三项累计量及预计到达时间。服务时间暂为 0，窗口尚不执行。每个配送点只安排一次服务，但道路和通行节点可以重复经过。

**最优性口径已明确：** 本阶段按用户要求使用贪心最近邻 + Dijkstra，不承诺整条巡回路线全局最优。成本贪心甚至可能得到比距离贪心更贵的完整路线；示例中如实保留该现象。后续插入法、局部优化或小规模精确算法可以作为单独迭代。

**载重与仓库现状：** 默认从字典序最小的仓库出发，支持显式选择并返回该仓库。提供可选 capacity_kg，检查全部所选节点默认需求量之和；省略时不校验载重。超载反馈失败，不默认回仓补货、多车或多趟。后续独立订单需要以实际货物量替代节点默认需求量。

**验收点：** 两种策略可切换；路线方向与道路一致；覆盖所有被接受的待配送订单且返回出发仓库；检查载重；不可达或未找到可行计划时反馈原因，不输出伪成功结果。

### FR-04 时间窗口

**原文扩展要求：** “加入时间窗口硬约束”，超出规定时间送达则标记“超时订单”并记录 penalty。

**原文歧义：** 严格硬约束通常排除迟到路线，但原文同时要求超时记录。建议采用“计划阶段检查窗口，运行阶段记录实际违约”的口径；这是设计解释，不是原文另行规定。

**设计建议：** 对窗口 `[earliest, latest]`，提前到达可等待，送达时间为 `max(arrival, earliest)`；迟到分钟数为 `max(0, delivered_at - latest)`。初版建议服务时长取 0，并在实现时明确该假设。

**不可行处理建议：** 调整顺序后仍找不到可行方案时，将订单标记为待处理并说明原因；预计迟到显示预警，实际迟到才记录超时。启发式搜索失败应称为“未找到可行方案”，不能据此证明不存在可行方案。

**penalty 待定：** 原文没有公式。可采用 `penalty = rate * late_minutes`，例如 `rate = 1 分/分钟`，将 rate 放入配置；此值仅为候选方案。本阶段只保留记录字段，不固化系数。处罚分与运输成本分别统计；若允许用处罚换取迟到，属于软约束模式，需另行确认。

**验收点：** 早到、按时、恰好截止和迟到均正确处理；区分预计迟到和实际超时；处罚记录可追溯。

### FR-05 动态订单

**原文要求：** 配送过程中响应新订单；扩展要求插入紧急订单并优先满足，如“1 小时内送达”。

**设计建议：** 新订单进入统一订单集合，尝试插入尚未完成路线的各个位置，检查新增代价、全部后续时间窗口与载重。紧急订单优先处理，但不默默取消已有订单的时限约束。找不到可行插入位置时标为待处理并反馈。

**货物来源待定：** 车辆载重有空余并不等于新订单货物已在车上。原文未给出途中新订单的取货规则；第 4 阶段应明确演示假设或取货流程，再决定是否可直接插入，不默认车辆能够凭空取得货物。

**验收点：** 配送途中可新增订单；成功时只更新剩余任务；失败时保留原有可行计划并说明原因；已完成订单不重复配送。

### FR-06 模拟时钟

**来源：** 本次用户明确提出，也是时间窗口、在途状态与路况事件的实现支撑；题目没有单列时钟操作要求。

**设计建议：** 使用相对模拟日开始的分钟数，独立于电脑真实时间；界面可转换成时分显示。后续支持推进和暂停，所有订单、移动和路况事件使用同一时间基准，便于可重复演示。

**验收点：** 时间单调推进，暂停不推进；等待、行驶和截止判断共用时钟。模拟时间与墙上实际经过的时间不混用。

### FR-07 车辆当前位置

**来源：** 本次用户明确提出，也是动态重规划的必要运行状态；题目未规定具体表示方法。

**设计：** `VehiclePosition` 区分“位于节点”和“位于有向道路上”，后者保存道路 ID 及进度；初始化后只能处于一种有效状态。`Vehicle` 保存载重上限、当前载荷和出发仓库。

**在途重规划建议：** 从下一可执行位置衔接新路线，已走过的部分保持不变。初版可采用先走完当前道路再转向的规则；道路关闭或删边发生在正在行驶的边上时，应明确处理策略，不能让车辆瞬移。该策略在第 4/5 阶段定稿。

**验收点：** 位置随时钟推进；路线更新不使车辆跳回仓库；已完成配送和已走过道路不会被重复执行。

### FR-08 实时路况与重规划

**原文扩展要求：** 道路具有拥堵、畅通等动态属性；因拥堵导致某条路径耗时增加 20%以上时自动触发重新规划，并在界面更新路径高亮。

**设计：** 道路保留初始耗时和当前耗时，路况事件记录变化前后数值。重新评估距离/成本目标下的剩余路线及时间可行性；耗时增加不一定会改变距离最短路线，允许重新评估后仍保留同一条路线，不应为了演示而强行改变路线。

**待定基准：** “增加 20%以上”按含 20% 处理；相对初始耗时、上次耗时还是上次规划快照，原文未明确。第 5 阶段须选定统一比较基准，处理重复触发及零基准，不能悄悄切换比较口径。

**原文实现提示：** 可用随机数模拟变化，例如每 30 秒修改 10% 道路耗时；这些数值是示例，不是硬性参数。原文提示使用增量式更新，仅调整受影响路段；计划先验证重规划正确性，再优化受影响范围。随机种子、更新频率及比例建议可配置，以便复现。

**验收点：** 检查阈值两侧及边界、连续事件；触发后基于车辆状态与未完成订单重新评估；界面展示当前路况和有效路线。

### FR-09 可视化

**原文基本要求：** 图形界面展示节点位置、道路方向、权重标签；扩展要求在重规划后更新路径高亮。

**第 3 阶段实现：** 按本次允许的简化方案，C++ 的 `Visualizer` 导出 5 份 CSV，Python/matplotlib 读取并生成网络与路线图，展示节点坐标、类型、有向箭头、选定权重与路线步号。支持可选绘图窗口，暂不提供集成式动态调度 GUI。既有 `NetworkView` 接口保留供后续使用；窗口/路况变化后的自动刷新仍属后续范围。

**验收点：** 节点坐标与配置对应；方向及权重可辨识；高亮对应当前路线，重规划后旧高亮不会残留。时钟、车辆位置与订单状态展示属于配合动态功能的设计建议。

## 实现前需明确的规则

这些规则可以随对应阶段落实，不阻塞当前骨架交付：

1. 第 2 阶段已明确：JSON 网络格式、示例需求量单位 kg、时间单位分钟。初始仓库和模拟开始时间字段将在加载车辆/订单时补充。
2. 第 3 阶段已明确：贪心最近邻 + Dijkstra；CSV + Python/matplotlib 绘图；可选的单次装载量校验。没有提前实现动态订单或窗口约束。
3. 第 4 阶段：硬约束与超时记录的解释、penalty 系数、服务时长、新订单取货来源和在途转向规则。
4. 第 5 阶段：拥堵百分比的比较基准、零基准与重复触发策略、道路在途关闭规则及增量更新范围。

不在本阶段新增数据库、联网地图、账户系统、多车辆调度、真实 GPS 或真实交通数据接入等原文未明确要求的功能。
